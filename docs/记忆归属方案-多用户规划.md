# 记忆归属方案：从「全局单流」到「按人分档」

> 【项目总监：规划文档】
> 日期：2026-10-02
> 状态：阶段 1 已实施；阶段 2/3 待排期
> 关联：`语音对话状态机与音频前端.md`、`v1架构方案-纯CPU适配.md`

---

## 一、问题

当前所有对话写入**同一张 `messages` 表、同一条记忆流**（"全局单流"）。后果：

1. **多孩子串味**：二宝会听到"大宝"的记忆（"你上次说你喜欢恐龙呀"——其实没说过）
2. **无法按人/按次回看或删除**
3. **长期记忆无法区分人**：一份档案混所有孩子的信息

**根因：系统没有身份信号。** 声纹是「每轮自确立、静默超时释放」的（设计如此，见状态机 ADR §2.1），
除了"本轮目标说话人"，对说话人一无所知。

---

## 二、四个方案

| 方案 | 怎么知道"是谁" | 优 | 劣 |
|---|---|---|---|
| **A. 不区分**（现状） | — | 零成本 | 多孩子串味；无法按人回看 |
| **B. 声纹自动建档** ⭐推荐 | 每轮声纹 vs 档案库比对（阈值 0.5）：匹配→归入，不匹配→新建档案 | **全自动、零额外交互**；复用现有每轮声纹 | 档案可能建错（但**不致命**，见 §三） |
| C. 显式选择 | 前端选"大宝/二宝" | 100% 准确 | 破坏"打开就说"；孩子会乱点 |
| D. 每人一个唤醒词 | 唤醒词区分 | 天然区分 | 要每人记不同的词，不现实 |

---

## 三、为什么 B 不会重蹈"全局注册"的覆辙

早期做过「全局注册声纹」并踩坑（注册成家长声纹 → 孩子说话全被过滤 → 永久失效）。**B 与它本质不同**：

| | 旧的全局注册 | B 的自动建档 |
|---|---|---|
| 档案数量 | **唯一一个** | 可以有多个 |
| 建错了 | **永久锁死**，无自愈路径 | 下轮不匹配 → 新建档案，**自动恢复** |
| 人工干预 | 只能删库 | 可加"改名 / 合并 / 删除档案"入口 |
| 前提 | 需要一次"正确的注册" | 不需要注册，自然积累 |

**关键设计**：每轮对话结束时，把**本轮声纹**和档案库比对——
- 相似度 ≥ 0.5 → 归入该档案
- 都不匹配 → 新建档案（"新朋友"）

完全复用现有「每轮声纹」，只多一步持久化 + 比对。**不需要任何额外交互。**

## 五、阶段 1 已实施细节（长期记忆）

### 机制

```
会话结束（静默超时 30s / WebSocket 断连）
  → 取「自上次摘要以来」的新消息（水位线 profile.last_message_id）
  → 连同已有档案一起喂 LLM：
     「提取值得长期记住的：名字/年龄/喜好/家庭成员/重要事件/已讲过的故事标题；
       合并去重；忽略寒暄；≤300 字」
  → 写回 profile.facts，推进水位线
  → 之后每轮对话把 facts 注入 system prompt
```

### 表结构

```sql
CREATE TABLE profile (
    id SERIAL PRIMARY KEY,
    scope TEXT NOT NULL UNIQUE DEFAULT 'default',  -- 阶段 3 改为 speaker_id
    facts TEXT DEFAULT '',
    last_message_id INTEGER DEFAULT 0,             -- 摘要水位线（增量摘要，不重复）
    updated_at TIMESTAMPTZ DEFAULT now()
);
```

### 实测效果

输入对话（含名字/年龄/喜好/宠物/故事）→ 摘要输出：

```
小明，五岁。喜欢小兔子，喜欢蓝色。家里养了一只小猫，叫咪咪。
已讲过的故事：《小白兔采蘑菇》。
```

信息更新（孩子改口"现在喜欢红色"）→ 合并结果保留旧信息并更新：

```
小明，五岁。喜欢小兔子，现在喜欢红色。家里养了一只小猫，叫咪咪。
已讲过的故事：《小白兔采蘑菇》。明天要去幼儿园表演节目，唱唱歌。
```

注入验证（问"我叫什么名字"）：

| | 回复 |
|---|---|
| 有档案 | 「你叫小明呀，今年五岁啦。小月记得清清楚楚哦！」 |
| 无档案 | 「哎呀，小月还不知道你叫什么名字、几岁呢…」 |

### 成本

- 每次**会话结束**多 1 次 LLM 调用（约 500~800 tokens）
- 每轮对话 prompt 多约 300 字（≈300 tokens），相对 128K 窗口可忽略

### 相关约束

- **幂等**：靠水位线，重复触发不会重复摘要；用 `asyncio.Lock` 防多连接并发
- **消息太少不摘要**：少于 4 条新消息直接跳过（不值得）
- **失败不影响对话**：摘要失败只打日志，语音链路不受影响

## 六、阶段 2 设计（会话分组，待排期）

- `messages` 加回 `conversation_id`；每次 WebSocket 连接建一个会话
- **不改变记忆行为**（仍全局喂 LLM），只为支持"按会话回看/删除"
- 收益：将来能实现"忘掉昨天聊的"、按会话导出

> 注：早期版本有 `conversation_id` 但从未写入（恒 NULL），本次评审已移除。
> 阶段 2 是**重新引入并真正使用**。

## 七、阶段 3 设计（声纹档案，待排期）

### 表结构（草案）

```sql
CREATE TABLE speakers (
    id SERIAL PRIMARY KEY,
    name TEXT DEFAULT '新朋友',      -- 可人工改名
    embedding vector(192),
    created_at TIMESTAMPTZ DEFAULT now(),
    last_seen_at TIMESTAMPTZ DEFAULT now()
);
```

### 流程

```
每轮对话结束（已有 reference_embedding）
  → 与 speakers 表逐个比对（余弦）
  → 最高相似度 ≥ 0.5 → 归入该档案；否则 → 新建档案
  → 若本轮有对话内容 → messages.speaker_id 归属；长期记忆 scope = speaker_id
```

### 风险与对策

| 风险 | 对策 |
|---|---|
| 首次建档时混入家长声纹 | 多档案机制可自愈（下轮不匹配会新建）；提供人工改名/删除入口 |
| 孩子感冒/变声导致匹配失败 | 每次成功匹配更新 `last_seen_at` 并**滚动平均**声纹（渐进适应） |
| 档案碎片化（同一人建多个档案） | 提供"合并档案"入口；或按相似度聚类定期合并 |
| 家长说唤醒词建立"家长档案" | 家长档案不会收到孩子的记忆；且家长档案可标记为"忽略" |
